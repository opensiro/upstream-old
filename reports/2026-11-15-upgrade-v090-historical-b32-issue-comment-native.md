## Verified demand: first-party yottacode #291

At pinned current `yottadynamics/yottacode@3f388ee03db7fbf0ec44c368a59bfd32822d1730` (same GitHub default-head SHA before and after this experiment, MIT), first-party [issue #291](https://github.com/yottadynamics/yottacode/issues/291) describes a precise unmet operator task: an agent can **create and read** issues using typed GitHub tools, and **comment on pull requests**, but cannot **post a top-level comment on an existing Issue** without invoking `gh issue comment` through shell or opening GitHub UI. A developer with a working native GitHub token but no separately authenticated `gh` CLI cannot finish that issue-followup workflow using current agent tool surfaces.

**New bounded actor → trigger → action → output:** developer asks the agent to add a correction/follow-up to existing GitHub Issue #7 → the tool `issue_add_comment(number=7,body=...)` displays the full body for user approval, validates issue identity, calls typed GitHub Issue comment API → returns a typed `posted=true url=... id=...` result. When refused or unavailable, no write occurs and a distinguished `validation`, `not_found`, `github_unavailable`, or `github_error` outcome is shown. No approval is inferred; the current permission engine retains user-configured `Github(add_issue_comment)` `allow/ask/deny` matching and deny precedence.

**Original mechanism:** [`internal/github/interface.go`](https://github.com/yottadynamics/yottacode/blob/3f388ee03db7fbf0ec44c368a59bfd32822d1730/internal/github/interface.go) shipped `ReadIssue`, `ListOpenIssues`, `CreateIssue`, and `AddPRComment`, with no `AddIssueComment`. [`internal/agentruntime/runtime.go`](https://github.com/yottadynamics/yottacode/blob/3f388ee03db7fbf0ec44c368a59bfd32822d1730/internal/agentruntime/runtime.go) registered existing tools, not the new user action. The original missing typed operation is not evidence of user demand *alone*; demand is explicitly anchored to #291, which specifies new issue update/comment tools, approval and validation.

**Source-first attribution:** `GENERAL_UPSTREAM / SOURCE_FIRST MINOR_FEATURE`. This operator story was found in a live maintainer issue **after** the frozen pre-source S2 hypothesis about `validateWritePartition`, and is **not** `ASSESSMENT_DERIVED`, a repaired partition flaw or new VSM grade evidence.

Patch SHA256: `ccb0fca2cbc608a3fd0bd3c170443f59393826a367de5944e71e260f5115a457`, 18,988 bytes, **341 additions/2 deletions**. Code, tests and [`docs/github.md`](https://github.com/yottadynamics/yottacode/blob/3f388ee03db7fbf0ec44c368a59bfd32822d1730/docs/github.md) changed *only in the disposable checkout*.

The prototype deliberately handles the **`issue_add_comment` slice only**. #291 also requests `issue_update` (title/body, optional labels), which is **not implemented or claimed**. The typed original client first `GET /repos/o/r/issues/7` to verify it is an Issue, explicitly refuses a PR-shaped `pull_request` response, then `POST /repos/o/r/issues/7/comments`; it never directly posts to a live GitHub account in the local test. The existing `CachingClient` invalidates Issue-detail snapshots on successful mutation so a subsequent `issue_read` does not return stale comments. The source-native `Github(add_issue_comment)` target integrates with user permission matching; no special bypass or new policy privilege. It adds tool description, schema, typed body/number validation, mandatory `RequiresApproval`, actual runtime registration, and documentation.
